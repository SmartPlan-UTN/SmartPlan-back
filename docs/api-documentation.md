# OpenAPI and Swagger

The running API publishes its interactive OpenAPI documentation at
`http://localhost:3001/api/docs`. The raw contract is available at
`http://localhost:3001/api/docs-json` and can be imported into API clients or
used to generate frontend types.

The document includes every controller route under the global `/api` prefix.
DTO schemas, including required fields, validation constraints, query
parameters, and request bodies, are generated by the Nest Swagger compiler
plugin from TypeScript and `class-validator` metadata.

## Authentication

Endpoints marked with the lock icon require a JWT access token. In Swagger UI,
select **Authorize**, enter the token without the `Bearer` prefix, and execute
the request. Refresh tokens remain HTTP-only cookies and are never part of the
documented response body.

Public endpoints do not require authorization. Permission and role enforcement
still happens on the server; Swagger describes the shared `401` and `403` error
contracts for protected controller groups.

## Maintaining the contract

Every new controller must use `@ApiController({ tag, authenticated })` from
`src/common/swagger/api-controller.decorator.ts` in addition to Nest's
`@Controller`. It adds the tag, JWT scheme when applicable, and the standard
error responses. Keep tags user-oriented and in English.

Use DTOs for every body and query input. Do not replace them with raw request
objects: besides bypassing validation, raw objects cannot produce a reliable
OpenAPI schema. Add `@ApiProperty` or `@ApiPropertyOptional` whenever a field
cannot be inferred by the compiler plugin, such as a generic response wrapper,
union, or manually assembled response.

For an endpoint with non-standard success or error behavior, add the relevant
`@nestjs/swagger` decorators directly (`@ApiOperation`, `@ApiCreatedResponse`,
`@ApiOkResponse`, `@ApiNoContentResponse`, `@ApiNotFoundResponse`, and so on).
Use the existing `ErrorResponseDto` schema for API errors; it matches the global
HTTP exception filter.

## Logging

TypeORM logging is disabled in every environment. It therefore never logs SQL
statements, bound values, or database error queries. Application and worker logs
must describe the event and safe identifiers, never passwords, tokens, full
request bodies, or external-provider payloads.

Every HTTP response exposes `X-Request-Id`. The API accepts a safe client-sent
`x-request-id` too; otherwise it generates one. Failed responses include that
same value in `requestId`, so the frontend can report it and an operator can
find the corresponding structured server event without exposing implementation
details.

Successful requests generate `http_request_completed`; rejected client requests
generate `http_request_rejected`; unexpected server failures generate
`http_request_failed`. These events include only `requestId`, HTTP method,
route, status code, and duration where applicable.
