Repository progress status. It is the project's memory between sessions: anyone
arriving here (person or AI agent) should be able to resume without rereading the
entire Git history.

## How to update this file

**Update it when you finish a task, not when you start it.**

1. Find the row for the CU or task you worked on.
2. Change the **Status** according to the table below.
3. Complete **Branch** and **PR**.
4. If you made a technical decision that is not obvious from reading the code, add it to
   [Decisions](#decisions).
5. Add a dated entry to the [Log](#log).

### Statuses

| Status        | Meaning                                    |
| ------------- | ------------------------------------------ |
| `Not started` | No one has taken it yet                    |
| `In progress` | There is an open branch with actual work   |
| `In review`   | Open PR, awaiting 2 approvals              |
| `Completed`   | Merged into `develop`                      |
| `Blocked`     | Cannot proceed; the reason goes in Notes   |

### Rules

- A CU only moves to `Completed` when its PR is **merged**, not when it is open.
- A CU is not marked `Completed` without at least one happy-path test.
- Do not delete rows. If something is discarded, mark it `Blocked` and explain why.
- Dates use the `YYYY-MM-DD` format.

## Known pending items

Detected items that do not yet have an owner:

- Global `ValidationPipe` is not configured yet. `class-validator` and
  `class-transformer` are already dependencies (introduced with environment
  validation), so it only needs registration in `main.ts` with `whitelist: true`.
- The `lint` script includes `--fix`, making it unsuitable as a CI check. It should
  be split into `lint` and `lint:fix`.
- `no-explicit-any` is `off` here and `error` in the frontend. The criterion must
  be aligned.
- The database engine is decided in code (PostgreSQL), but not in the delivery
  document, which only says "relational database."
- **`ConfigModule` uses `cache: true`, so `ConfigService.get()` returns the raw
  `process.env` value (string), not the value typed by `validarEntorno`.**
  `database.config.ts` compensates manually for `DB_SSL` and `DB_PORT`. Decide
  whether to remove `cache` or document that `ConfigService` does not return typed
  values and every consumer must convert them.
- Since F01, `pnpm test:e2e` boots the complete `AppModule`, so **it requires the
  database to be running** (`pnpm db:up`). F13 isolated it in `smartplan_test` and
  creates it automatically, but the PostgreSQL server must still be available.
- The initial migration (`EsquemaInicial`) creates all 37 tables at once. From now
  on, **every entity change needs its own migration** (`pnpm migration:generate`):
  in development, `synchronize` adjusts the schema automatically and is easy to
  overlook, but it is disabled in production and migrations are the only mechanism
  that changes the schema.
- The traceability matrix and diagram do not agree on every attribute. The matrix
  governs functional behavior: `rating` references `actividad`, every `plan` keeps
  its owner, and coordinates remain in `activity_place` because they represent the
  meeting point.
- The only Appendix No. 5 class that still has no readable name is the catalog
  referenced by `plan_request.id_outing_type`. It is implemented as `outing_type`;
  if the original diagram calls it something else, this is a table rename.
  `feedback` and `plan_status` have already been completed against the diagram.
- `feedback` does not show `id_feedback_status` among its attributes, but the
  diagram draws the relationship with `feedback_status`. The column exists because
  the relationship cannot be implemented without it.
- **CU58 (view system metrics) has no dedicated tables.** `reporte` and
  `tipo_reporte` are out of scope, so REP-01 and REP-02 are solved with queries on
  the rest of the model. They return if user-created reports need to be saved.
- The core `skills/` (`00-project`, `01-domain`, `02-git-flow`) is duplicated in
  `SmartPlan-front`. Replicate any modification in the other repository.
- **Pending replication in `SmartPlan-front`:** the change from Jira to GitHub
  Issues in `skills/00-project/SKILL.md` and `skills/02-git-flow/SKILL.md`
  (2026-08-11). Until replicated, the frontend documents an unused branch
